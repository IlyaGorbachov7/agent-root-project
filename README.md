# agent-root-project
КПРА(старое название СУПР - Система управления проектом разработки) - Кореновой подход к разработке агентом. Организация каталогов и репозиториев в древовидном стиле, чтобы максильно информации было доступно агенту. Команды выполняются в корне.

Корневой workspace для агента: общие инструменты агента, спецификации, документация, DevOps и проекты. Репозиторий открывают целиком, чтобы агент видел и корень, и все подпроекты. Общие rules и skills лежат в `.cursor/`.
Можно не создавать отдельный гит репозиторий, а расположить данный проект там, где у нас доска, для каждого проекта у нас есть общая доска, тогда получается упрощаем, убрав один гит репозиторий.

Каталоги ниже — местная заготовка в этом репозитории. Отдельные remote и submodule здесь не подключены. В рабочем использовании часть каталогов заменяется своими git-репозиториями, и корень записывает их как submodule. Каталога `openspec/` в заготовке нет: это один отдельный git-репозиторий со спецификациями, в корне submodule с путём `openspec`. Первый раз этот репозиторий создают вместе с первой спецификацией и затем подключают. Каталога `docs/` в заготовке нет: это один отдельный git-репозиторий с документацией для людей, в корне submodule с путём `docs`.

README.md - данный файл описаывает общую информацию по проекту, текущий README.md заменяется полностью, можно добавить ссылку на базовую документацию https://gitlab.gdev.by/gdev-company-group/work/agent-root-project

Как воссоздали структуру, перед началом необходимо, чтобы агент описал всю структуру с подмодулями. Это делается ОДИН раз, когда рувоводитель проекта готовит данный проект, например: **Подготовь для работы агента проект(удалив общую информацию из текущего AGENTS.md файла), так же опиши в базовом README общую информацию по вложенным проектам(для человека). И для каждого проекта подготовь более детальное описание для работы с агентом и для человека README, работать будем с помощью агента на уровне корня данного проекта**.  Что касается docs, devops и другких корневых директорий: может быть как один гит репозиторий или может быть несколько гит директорий в каждой директории(docs,devops). Если у вас планируется один гит репозиторий(для простых проектов), то не зачем создать директорию в директории.

## Зачем эта структура

Подход собирает несколько проектов с общим поведением, инфраструктурой и способом работы агента. Корень workspace даёт одну картину, а релиз каждого проекта остаётся в своём git.

- Поведение можно описать в `openspec/specs/` по [OpenSpec](https://openspec.dev/). Это не обязательно для каждого проекта: чаще всего так делают там, где изменение ведёт агент. Тогда правка начинается в `openspec/changes/`: одно намерение, дельты по затронутым проектам, чеклист в `tasks.md`. Реализацию разносят по `projects/`, а требование остаётся в общей спецификации. Проект, который люди меняют сами, обходится README сервиса и `docs/`.
- Агент открывает корень и видит вызывающий сервис, контракт и инфраструктуру рядом с кодом, который правит. Правка в одном проекте опирается на соседние проекты в том же workspace.
- Правила и skills в `.cursor/` общие для всех проектов этого подхода. Новый сервис из `projects/_template/` документируют и меняют теми же правилами, что и остальные.
- Релизы независимы. У проекта, у `openspec/`, у `docs/` и у каждого репозитория под `devops/` свой git и свой цикл. Подход связан корнем, спецификацией и общими шаблонами. Код сервиса коммитится в его собственный репозиторий. Спецификации коммитят в репозиторий `openspec`.
- Инфраструктура, шаблоны пайплайнов и локальный стек лежат в `devops/` один раз. Проект подключает их из своего CI и Dockerfile.
- Люди и агент читают разные слои. Архитектура, ADR и runbook — в `docs/`. Если поведение ведут через OpenSpec, текущие требования и предлагаемые изменения — в `openspec/`. Инструкции агенту — в `.cursor/docs/`.

## Структура

```text
cursor-base/
├── AGENTS.md                 # карта workspace для агента
├── README.md
├── .cursor/                  # общие rules, skills и инструкции агенту
│   ├── rules/
│   ├── skills/
│   └── docs/
├── openspec/                 # submodule; для проектов, которые ведёт агент
│   ├── specs/
│   └── changes/
├── docs/                     # submodule; в заготовке нет
├── devops/                   # не репозиторий, контейнер для репозиториев DevOps
│   ├── platform/             # отдельный git
│   ├── ci-templates/         # отдельный git
│   └── local-compose/        # отдельный git
└── projects/
    └── _template/            # образец; каждый проект — свой git
```

Границы репозиториев:

- Корень — свой git. В нём `AGENTS.md` и `.cursor/`.
- `openspec/` — один отдельный git со спецификациями поведения, в корне записан как submodule. Он не обязателен для каждого проекта: чаще всего его заводят там, где работу ведёт агент. Если репозиторий уже есть, его подключают с путём `openspec`. Первый раз его создают вместе с первой спецификацией и затем подключают.
- `docs/` — один отдельный git с архитектурой, ADR и runbook, в корне записан как submodule с путём `docs`.
- `devops/` сам репозиторием не является. В примере внутри три репозитория: `platform`, `ci-templates`, `local-compose`. Если DevOps один, тот же приём с одной записью submodule `path = devops`.
- `projects/<имя>/` — отдельный git на каждый проект, в корне записан как submodule. `_template` показывает, что копировать в новый проект.

## Submodule

Submodule — запись в родительском git о вложенном репозитории: путь и конкретный коммит. Файлы вложенного репозитория лежат в рабочем каталоге, его история и remote остаются у него. Родитель хранит указатель на коммит, а не копию этой истории.

Так к корню подключают `docs/`, `openspec/`, `projects/<имя>/` и репозитории под `devops/`: по отдельности `platform`, `ci-templates`, `local-compose` либо один репозиторий с путём `devops`.

Что это даёт:

- У вложенного репозитория свой цикл коммитов и релизов. Сервис выпускают из репозитория проекта, документацию коммитят в `docs`, спецификации — в `openspec`.
- Корень фиксирует, какие коммиты документации, спецификаций, проектов и DevOps составляют один workspace. Соседний сервис, документация и инфраструктура открываются вместе в известных ревизиях. Агент правит один проект и видит остальные в тех же коммитах.
- Клон корня забирает именно эти ревизии:

  ```bash
  git clone --recurse-submodules <url-корня>
  ```

  Если корень уже склонирован без `--recurse-submodules`, или после `git pull` в корне появились новые записи submodule, рабочую копию готового workspace собирают из корня:

  ```bash
  git submodule update --init --recursive
  ```

  Команда подтягивает все вложенные репозитории на коммиты, которые зафиксированы в текущем `HEAD` корня: `docs/`, `openspec/`, `projects/<имя>/` и репозитории под `devops/`. Вложенные submodule, если они есть, инициализируются рекурсивно.

  Сдвиг указателя — отдельный коммит в корне. Сначала коммит делают в репозитории документации, спецификаций, проекта или DevOps, затем корень записывает новый коммит submodule.
- Пока своего remote нет, каталог остаётся файлами корневого репозитория. Submodule появляется, когда remote уже есть.

Каталог ещё свободен, репозиторий берут с remote. Команда создаёт каталог, дописывает `.gitmodules` и ставит в индекс ссылку на текущий коммит ветки `main`:

```bash
git submodule add -b main <url-docs> docs
git submodule add -b main <url-openspec> openspec
git submodule add -b main <url-проекта> projects/billing
```

Дальше коммит делают в корне, как в примере ниже. У репозитория к этому моменту есть хотя бы один коммит: пустой репозиторий даёт в индексе нулевой SHA.

### Подключить локальный проект

Клон, который уже есть на машине, копируют в тот каталог workspace, где его будут использовать. Проект кладут в `projects/<имя>`, например `projects/billing`. Документацию кладут в `docs/` в корне workspace. Спецификации кладут в `openspec/`. Исходный клон остаётся на своём месте. Команды выполняют из корня workspace.

В примере проект называется `billing`, ветка `main`, адрес remote — `<url-проекта>`. В URL пишут remote репозитория. У клона к этому моменту есть хотя бы один коммит: пустой репозиторий даёт в индексе нулевой SHA. То же условие у клонов `docs` и `openspec`.

Каталог назначения ещё свободен. Копируют клон целиком, вместе с каталогом `.git`:

```bash
cp -a <путь-к-клону> projects/billing
```

Документацию и спецификации копируют так же, в свои каталоги:

```bash
cp -a <путь-к-клону> docs
cp -a <путь-к-клону> openspec
```

После копирования каталог непустой. `git submodule add` такой путь не принимает, запись делают вручную. Так подключают проект, `docs` и `openspec`. Клон стоит на ветке, чей коммит нужно зафиксировать.

В примере проект `billing`:

```bash
git config -f .gitmodules submodule.projects/billing.path projects/billing
git config -f .gitmodules submodule.projects/billing.url <url-проекта>
git config -f .gitmodules submodule.projects/billing.branch main
git add .gitmodules projects/billing
```

`git add projects/billing` записывает в индекс режим `160000` и SHA текущего `HEAD`. В историю корня попадает этот указатель. `.gitmodules` входит в тот же коммит: в нём лежат путь и URL.

Для документации и спецификаций те же команды, другие ключи и пути:

```bash
git config -f .gitmodules submodule.docs.path docs
git config -f .gitmodules submodule.docs.url <url-docs>
git config -f .gitmodules submodule.docs.branch main
git add .gitmodules docs

git config -f .gitmodules submodule.openspec.path openspec
git config -f .gitmodules submodule.openspec.url <url-openspec>
git config -f .gitmodules submodule.openspec.branch main
git add .gitmodules openspec
```

`git add docs` и `git add openspec` записывают тот же режим `160000` и SHA текущего `HEAD` своего клона.

Дальше коммит делают в корне. Во вложенном репозитории новый коммит нужен, когда меняется его содержимое. Если `HEAD` уже тот, который должен видеть workspace, во вложенном репозитории коммитить нечего.

```bash
git add .gitmodules
git commit -m "Add billing submodule"
git submodule init
```

Если `.git` после копирования остался каталогом, его переносят в модули корня. После этого checkout выглядит так же, как после `git submodule add`:

```bash
git submodule absorbgitdirs
```

Проверка из корня: `git submodule status` показывает SHA без минуса в начале строки, `git ls-tree HEAD <путь>` — тот же SHA, что `git -C <путь> rev-parse HEAD`. Для примера путь — `projects/billing`, для документации `docs`, для спецификаций `openspec`.

Следующий коммит вложенного репозитория пушат в его remote. Затем корень записывает новый SHA:

```bash
git add projects/billing
git commit -m "Bump billing submodule"
```

Для документации и спецификаций в `git add` путь `docs` или `openspec`.

## OpenSpec

Спецификации поведения системы по [OpenSpec](https://openspec.dev/). Каталог `openspec/` — один отдельный git-репозиторий, в корне записанный как submodule: путь `openspec` и конкретный коммит. Workspace открывают с корня, и агент видит и требования, и код. Коммиты спецификаций делают в репозитории `openspec`, затем корень записывает новый SHA. Раскладка совпадает с тем, что создаёт `openspec init`. Файл `config.yaml` необязателен, его добавляет CLI, когда нужна своя настройка.

Если репозиторий уже есть, его подключают из корня workspace — см. [Submodule](#submodule). Свободный каталог заполняет `git submodule add`. Клон, который уже есть на машине, копируют в `openspec/` и записывают вручную — см. [Подключить локальный проект](#подключить-локальный-проект).

Первый раз каталог создают вместе с первой спецификацией командой `openspec init` или `/opsx:propose` и сразу ведут как этот отдельный git. Когда в нём есть хотя бы один коммит, его подключают к корню тем же submodule.

`specs/` описывает, как система ведёт себя сейчас. `changes/` держит предлагаемые изменения, пока их не приняли. Документация для людей (архитектура, ADR, runbook) — отдельный репозиторий `docs/`, см. [Документация](#документация). Инструкции агенту — в `.cursor/docs/`.

### Нужен не каждому проекту

OpenSpec подключают не к каждому каталогу в `projects/`. Чаще всего он нужен там, где изменение делает агент. Требования тогда лежат в файлах до кода, и следующая сессия читает поведение из репозитория, а не из переписки.

Проект, который люди правят сами, может в `openspec/` не появляться. Для него хватает README сервиса, кода в `projects/<имя>/` и, когда нужно объяснить устройство, архитектуры и ADR в `docs/`.

| | Без OpenSpec | С OpenSpec |
| --- | --- | --- |
| Кто ведёт изменение | Люди пишут код по задаче | Агент реализует изменение по спецификации |
| Где описано поведение | Код, README проекта, архитектура и ADR в `docs/` | Текущее поведение в `openspec/specs/`, намерение этой правки в `openspec/changes/` |
| С чего начинают | Сразу правят `projects/<имя>/` | Сначала `proposal.md`, дельта и `tasks.md`, затем код |
| Несколько сервисов | Договорённость держат в задаче и в `docs/` | Одно изменение и дельты по затронутым проектам, код в каждом `projects/<имя>/` |
| Что остаётся после работы | Коммит в репозитории проекта | Принятые требования в `openspec/specs/`, история правки в `changes/archive/` |

Плюсы OpenSpec там, где работает агент:

- Агент видит, как система ведёт себя сейчас и что меняют в этот раз. Следующая сессия читает те же файлы.
- Намерение смотрят до кода: границы в `proposal.md`, объём в `tasks.md`.
- Правка нескольких сервисов остаётся одним каталогом. Код расходится по проектам, общее требование остаётся в спецификации.
- После архивации источник поведения — `specs/`. Чат для этого не нужен.

Минусы:

- Небольшая правка, которую человек делает сам, обрастает файлами: `proposal.md`, `design.md`, дельта, `tasks.md`.
- Спецификация расходится с кодом, если изменение уже в проекте, а `/opsx:archive` не выполняли.
- Это отдельный репозиторий, подключённый к корню как submodule: коммит делают в `openspec`, затем корень записывает новый SHA.
- Проекту без агента формат ничего не прибавляет к README и `docs/`.

Каталог `openspec/` заводят, когда в workspace хотя бы один проект меняет агент. Остальные проекты в спецификациях могут не участвовать.

### Домен

Домен — одна область поведения, которую описывает отдельный `spec.md`. В файле собраны принятые требования к этой области: что система делает. Код, раскладка сервисов и инфраструктура в домен не входят: код лежит в `projects/`, устройство системы — в `docs/`.

Имя домена — каталог, в котором лежит `spec.md`. Его берут из смысла области, коротко: `auth`, `invoices`, `postings`.

Домен не совпадает с проектом. У `projects/billing/` может быть несколько доменов, `invoices` и `payments`. Если у сервиса одна область и её не делят, доменом служит сам сервис: каталог `billing`, файл `specs/billing/spec.md`. Общая область нескольких проектов — тоже один домен, например `auth`.

Идентификатор способности в OpenSpec — путь от `specs/` до каталога домена. У домена сразу под `specs/` это имя каталога: `auth` или `billing`. У домена внутри проекта путь длиннее: `billing/invoices`. Дельта изменения повторяет тот же путь.

### Каталоги

Пока доменов мало, их кладут сразу под `specs/`:

```text
openspec/
├── specs/
│   └── <домен>/
│       └── spec.md
├── changes/
│   ├── <имя-изменения>/
│   │   ├── proposal.md
│   │   ├── design.md
│   │   ├── tasks.md
│   │   └── specs/
│   │       └── <домен>/
│   │           └── spec.md
│   └── archive/
└── config.yaml                    # необязательно, создаёт openspec init
```

### Много спецификаций на разные проекты

Когда доменов много и они принадлежат разным проектам, первый каталог называет проект так же, как `projects/<имя>`. Внутри лежат домены этого проекта. Общий домен, например `auth`, остаётся сразу под `specs/`, рядом с проектными каталогами. Обе раскладки живут в одном `specs/`.

```text
openspec/
├── specs/
│   ├── billing/                         # projects/billing
│   │   ├── invoices/
│   │   │   └── spec.md                  # способность billing/invoices
│   │   └── payments/
│   │       └── spec.md                  # способность billing/payments
│   ├── ledger/                          # projects/ledger
│   │   └── postings/
│   │       └── spec.md                  # способность ledger/postings
│   └── auth/                            # общая способность
│       └── spec.md
├── changes/
│   ├── add-invoice-export/
│   │   ├── proposal.md
│   │   ├── design.md
│   │   ├── tasks.md
│   │   └── specs/                       # те же относительные пути, что в specs/
│   │       ├── billing/
│   │       │   └── invoices/
│   │       │       └── spec.md
│   │       └── ledger/
│   │           └── postings/
│   │               └── spec.md
│   └── archive/
│       └── YYYY-MM-DD-<имя>/
└── config.yaml
```

Правила раскладки:

- Один каталог в `changes/` — одно изменение. Активных изменений может быть несколько, каждое в своём каталоге.
- Имя изменения — короткое действие, например `add-invoice-export`.
- Дельта повторяет относительный путь способности. Для `openspec/specs/billing/invoices/spec.md` дельта лежит в `openspec/changes/<имя>/specs/billing/invoices/spec.md`. Идентификатор способности — `billing/invoices`.
- Изменение на несколько проектов остаётся одним каталогом. В `tasks.md` пункты раскладывают по `projects/<имя>/`, в дельте — по одному `spec.md` на каждую затронутую способность.
- У проекта одна способность — достаточно `openspec/specs/<проект>/<домен>/spec.md`. Отдельный `spec.md` прямо в `openspec/specs/` OpenSpec не читает: файл всегда лежит в каталоге способности.
- Пока изменение не архивировали, требований в `specs/` нет. Они попадают туда из дельты при архивации.
- Код, Dockerfile и CI в `openspec/` не кладут. Реализация — в `projects/<имя>/`.

### Артефакты изменения

Артефакты читают по порядку. Следующий опирается на предыдущий, а при реализации любой из них можно поправить, если выяснилось новое.

| Файл | Содержание |
| --- | --- |
| `proposal.md` | Зачем изменение, границы и ожидаемый результат |
| `specs/<проект>/<домен>/spec.md` | Дельта: какие требования добавить, заменить или убрать. Для плоского домена путь короче: `specs/<домен>/spec.md` |
| `design.md` | Технический подход и решения |
| `tasks.md` | Чеклист реализации, пункты `- [ ]` / `- [x]`. В пункте указывают проект, если изменение затрагивает несколько |

### Дельта

Дельта описывает разницу с текущим `specs/`, а не копирует всю спецификацию. Заголовки секций фиксированы, OpenSpec разбирает их при архивации:

```markdown
# Delta for Billing

## ADDED Requirements

### Requirement: Invoice Export
The system MUST export an invoice as a PDF file.

#### Scenario: Export from the invoice page
- GIVEN an open invoice
- WHEN the user requests an export
- THEN the system returns a PDF for that invoice

## MODIFIED Requirements

### Requirement: Invoice List
The system SHALL show the export status on each row.
(Previously: the list showed only number and amount)

#### Scenario: Status column
- GIVEN at least one invoice
- WHEN the user opens the list
- THEN each row shows whether a PDF export exists

## REMOVED Requirements

### Requirement: Email a Copy on Every Save
(Deprecated: export is explicit)
```

- `ADDED` — требования дописываются в основной `spec.md` способности.
- `MODIFIED` — требование с тем же именем заменяет прежнюю редакцию.
- `REMOVED` — требование удаляется из основного `spec.md`.

### Цикл

Команды `openspec ...` выполняют в терминале из корня workspace. Команды `/opsx:...` пишут в чат агента.

Установка CLI, если его ещё нет:

```bash
npm install -g @fission-ai/openspec@latest
```

Каталог `openspec/` к этой команде уже подключён как submodule либо только что создан как отдельный git. Дальше способности по проектам добавляют вложенными каталогами, как в раскладке выше. Коммит изменения и архива делают в репозитории `openspec`, затем корень записывает новый SHA.

Обычный путь (профиль `core`):

1. `/opsx:explore` — разобрать задачу до спецификации. Шаг необязательный.
2. `/opsx:propose <имя>` — агент создаёт `changes/<имя>/` и черновики `proposal.md`, дельты, `design.md`, `tasks.md`. Для нескольких проектов дельты кладут по путям `specs/<проект>/<домен>/spec.md`.
3. Просмотреть черновик и поправить его до кода.
4. `/opsx:apply` — выполнить пункты `tasks.md` в `projects/<имя>/`.
5. `/opsx:archive` — влить дельту в `specs/` и убрать изменение из активных.

Расширенный профиль включает `/opsx:new`, `/opsx:ff`, `/opsx:continue` и `/opsx:verify`. Его включают через `openspec config profile`, затем `openspec update`.

Проверка из терминала:

```bash
openspec list
openspec show add-invoice-export
openspec validate add-invoice-export
openspec view
```

### Архивация

`/opsx:archive` применяет дельту к `specs/<путь-способности>/spec.md` по правилам секций выше и переносит каталог изменения в `changes/archive/YYYY-MM-DD-<имя>/`. Архив остаётся историей. Актуальным описанием поведения после этого служит `specs/`.

## Документация

Один git-репозиторий с документацией для людей: архитектура, ADR и runbook. В заготовке каталога `docs/` нет. В рабочем использовании корень хранит его как submodule: путь `docs` и конкретный коммит. Подключают из корня workspace — см. [Submodule](#submodule). Свободный каталог заполняет:

```bash
git submodule add -b main <url-docs> docs
```

Клон, который уже есть на машине, копируют в `docs/` и записывают вручную — см. [Подключить локальный проект](#подключить-локальный-проект).

Дальше в нём ведут:

```text
docs/
├── architecture/              # как устроена система и как связаны сервисы
├── adr/                       # принятые решения
└── runbooks/                  # как сопровождать и разбирать сбои
```

Если поведение проекта ведут через OpenSpec, спецификация лежит в отдельном репозитории `openspec/`, тоже подключённом как submodule. Инструкции агенту лежат в `.cursor/docs/`. Коммиты документации делают в репозитории `docs`, затем корень записывает новый SHA.

## Как начать работать

### Уже подготовленный workspace

Когда руководитель проекта один раз описал структуру и в корне записаны submodule, разработчику достаточно получить корень и подтянуть вложенные репозитории. Клон с submodules сразу:

```bash
git clone --recurse-submodules <url-корня>
```

Если корень уже на диске (клон без `--recurse-submodules` или обновление после `git pull`), из каталога корня:

```bash
git submodule update --init --recursive
```

После этого открыть корень в Cursor: агент видит `docs/`, при необходимости `openspec/`, проекты в `projects/` и DevOps под `devops/` в тех коммитах, которые зафиксировал корень. Дальнейшие шаги — в README и `AGENTS.md` конкретных проектов и в `docs/`.

### Новый проект из заготовки

Новый проект ведут из этой заготовки. Работу начинают после подключения документации и, если репозиторий уже есть, спецификаций. Тогда в Cursor открывают корень workspace, и агент видит спецификации, документацию, DevOps и соседние проекты.

1. Клонировать корневой репозиторий. Если submodule уже записаны в корне, клонировать с `--recurse-submodules`: так приходят `docs/`, `openspec/`, проекты и репозитории под `devops/`. Иначе после клона выполнить `git submodule update --init --recursive` — см. [Submodule](#submodule).
2. Если `docs/` ещё не подключён, подключить репозиторий документации как submodule — см. [Документация](#документация).
3. Если в этом workspace пользуются спецификациями и `openspec/` ещё не подключён, подключить его как submodule — см. [OpenSpec](#openspec). Документацию и, при необходимости, спецификации подключают до открытия workspace.
4. Открыть корень workspace в Cursor.
5. Скопировать `projects/_template` в `projects/<имя>`.
6. Завести для этого каталога свой git-репозиторий и подключить его к корню как submodule с путём `projects/<имя>` — см. [Submodule](#submodule). Клон, который уже есть на машине, подключают по шагам из [Подключить локальный проект](#подключить-локальный-проект). Пока remote нет, каталог остаётся в корневом репозитории как местная заготовка.
7. Заменить `README.md` проекта: как его запустить, от чего он зависит, какие порты занимает. Добавить `AGENTS.md` с тем, что важно агенту только в этом проекте. Код класть в `src/`.
8. Если проект будет менять агент, описать первое изменение в OpenSpec из корня workspace. Если каталога `openspec/` ещё нет, его создают как отдельный git: `openspec init` или `/opsx:propose <имя-изменения>`. Спецификацию проекта кладут в `openspec/specs/<проект>/<домен>/spec.md` и коммитят в репозиторий `openspec`, затем корень записывает новый SHA. Когда в репозитории есть хотя бы один коммит, а submodule ещё нет, его подключают — см. [Submodule](#submodule). После ревью черновика `/opsx:apply` выполняет `tasks.md` в `projects/<имя>/`. Когда поведение принято, `/opsx:archive` вливает дельту в `openspec/specs/`. Проект, который ведут люди без агента, этот шаг пропускают.
9. Dockerfile и CI оставить в репозитории проекта. Общие пайплайны подключать из `devops/ci-templates/`, локальный стек — из `devops/local-compose/`. Подробности — в [devops/README.md](devops/README.md).
10. Архитектуру, ADR и runbook дописать в уже подключённый `docs/`. Коммит делают в репозитории `docs`, затем корень записывает новый SHA.

Более полные рекомендации по организации взаимодействия Cursor и кода: [Оформление микросервисных проектов для работы с агентами](https://gitlab.gdev.by/gdev-company-group/work/work/-/wikis/Structuring-microservice-projects-for-working-with-agents-(Cursor)).

## Советы

### Пуши и запросы на слияние

Агенту можно поручить отправку ветки на сервер и создание запроса на слияние. Для этого ему нужен токен GitLab того аккаунта, от имени которого пойдут push и merge request. Без токена агент готовит коммиты локально, а на сервер их отправляет человек.

Токену хватает прав на запись в репозиторий и на API запросов на слияние. Для всего workspace берут токен пользователя или группы, у которого есть доступ к каждому репозиторию, куда агент будет пушить: корень, `projects/<имя>/`, `docs/`, `openspec/`, репозитории под `devops/`. Токен одного проекта действует только в этом проекте. Роли Developer достаточно, чтобы пушить в обычную ветку и открывать merge request. В защищённую ветку, например основную, агент не пушит: он отправляет свою ветку и открывает запрос на слияние в неё.

Токен создают в GitLab и кладут в окружение машины, на которой запущен Cursor. В чат и в файлы репозитория его не пишут: чат остаётся в истории переписки, файл может уехать в коммит.

1. В GitLab открыть Access tokens. Для пользователя это настройки профиля, для проекта или группы — Settings → Access tokens.
2. Задать имя, срок действия и права `write_repository` и `api`. Создать токен и скопировать его сразу: GitLab показывает значение один раз.
3. В окружении пользователя, вне репозитория, задать переменные и перезапустить Cursor, чтобы агент их унаследовал:

   ```bash
   export GITLAB_TOKEN=<токен>
   export GITLAB_HOST=<хост-gitlab>
   ```

4. Один раз привязать GitLab CLI к этому токену. CLI хранит его в своём каталоге настроек, не в проекте. Если команды `glab` ещё нет, её ставят по инструкции [GitLab CLI](https://gitlab.com/gitlab-org/cli).

   ```bash
   glab auth login --hostname "$GITLAB_HOST" --token "$GITLAB_TOKEN"
   glab auth setup-git
   ```

   `setup-git` направляет `git push` через `glab`, поэтому токен не попадает в URL remote.

5. В задании агенту написать, что можно пушить ветку и открывать merge request. Токен при этом уже есть в окружении, повторять его в тексте задания не нужно.

Дальше агент отправляет текущую ветку и создаёт запрос на слияние:

```bash
git push -u origin HEAD
glab mr create --title "<заголовок>" --description "<описание>" --target-branch main
```

Имя целевой ветки берут из репозитория. Автор push и merge request — учётка, которой выдан токен. Когда срок токена вышел или он засветился, его отзывают в GitLab и выпускают новый.
